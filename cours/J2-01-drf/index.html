Les sérialiseurs

Ce qui entre n'a pas été vérifié ; ce qui sort n'est pas convertible

Le problème à poser, dans les deux sens : entrant, le corps d'une requête est du texte que personne n'a validé — n'importe quel client peut envoyer "prix": "gratuit". Sortant, le modèle porte des objets Python (Decimal, date) que JSON refuse. Deux problèmes, un seul objet qui les résout.

À la main, ça fuit dès la première exception

def detail(request, pk):
    p = Produit.objects.get(pk=pk)
    return JsonResponse({
        "nom": p.nom,
        "prix": str(p.prix),
    })
  • str(p.prix) : la conversion se fait champ par champ, dans chaque vue
  • p.categorie ? une clé étrangère ne se met pas en JSON — une ligne de plus
  • entrant : aucun contrôle — {"prix": "gratuit"} entre en base ou plante
  • les erreurs partent en texte libre, que le client devra parser
Slide de MOTIVATION : ne PAS donner le nom des solutions ici. La salle propose souvent « un to_dict() » — bonne intuition, et elle échoue au premier champ imbriqué ou au premier formulaire entrant. C'est exactement le trou que les frames font construire.

🎮 Valider, convertir, refuser

Six frames sur un décor unique (le modèle Produit du module II, devenu ModelSerializer). Déroulé : 1. Faire répondre chacun aux deux premières AVANT validation — les types (Decimal) et les champs requis sont là où l'intuition se trompe. 2. La frame « PUT amputé » prépare directement la découverte 4.3 du TP : DRF exige un PUT complet, contrairement au protocole brut. Ne pas la conclure soi-même. 3. La frame « survit » EST le piège du TP (stock qui reste à 12 après un PUT complet) : faire noter la prédiction noir sur blanc. 4. Terminer sur serializer.errors : c'est lui que le 400 met dans son corps, champ par champ. Erreur fréquente à guetter : croire que validated_data exige la sauvegarde. Il existe dès is_valid().

ViewSet et routeur

Deux URL, dix verbes possibles : qui décide quoi ?

Le problème à poser : une ressource REST standard, c'est deux adresses (la liste, le détail) et six opérations dessus — soit une douzaine de combinaisons URL × méthode à câbler à la main, chacune avec le bon code d'état. Écrire cela pour UN modèle prend une heure ; la boutique en a quatre. Demander combien de lignes de urlpatterns ils accepteraient d'écrire.

🎮 Deux URL : qui répond à quoi ?

Six frames. Points de passage : 1. Les deux premières font CONSTRUIRE la table verbe → action — celle du module I était du vocabulaire reçu, ici elle se déduit des actions fournies. 2. « POST sur le détail » : bien marquer la différence 405 / 400 / 404, les trois codes que la salle confond le plus. 3. « le 404 vient de la vue » fait le lien explicite avec le module II : le routeur trouve sa vue ici, alors qu'il échouait avant toute exécution sur /produits/abc/. Même code, deux origines, deux coûts. 4. « DELETE réussi » : 204, pas 200 — le même triage que le Jour 1, appliqué aux réponses d'un vrai framework. 5. La dernière nomme ModelViewSet et laisse ouvert ce qui autorise tout : ne pas développer, la partie 5 y revient par la question posée.

Récapitulatif — ce que cinq lignes produisent

class ProduitViewSet(viewsets.ModelViewSet):
    queryset = Produit.objects.all().order_by("id")
    serializer_class = ProduitSerializer

routeur = DefaultRouter()
routeur.register("produits", ProduitViewSet, basename="produit")
URL générée Verbes servis
/api/produits/GET → list · POST → create
/api/produits/<pk>/GET → retrieve · PUT → update · PATCH → partial_update · DELETE → destroy

La table est inscrite dans chaque motif généré (attribut actions) : routeur.urls se lit comme n'importe quel urlpatterns. Un mauvais verbe y répond 405 avec l'en-tête Allow.

Slide de RÉFÉRENCE, après les frames — la table était leur corrigé. Rappeler que DefaultRouter ajoute aussi la racine de l'API (/api/), vue en démonstration.

Vues génériques et requêtes cachées

La réponse est correcte ; la base, elle, encaisse

Le problème à poser : rien n'est cassé. La liste répond 200, le JSON est juste, les tests passent — et seize requêtes SQL sont parties pour huit produits parce que DEUX champs ont été ajoutés au sérialiseur. Le N+1 du module II vivait dans la vue ; celui-ci vit dans la conversion. Demander où, selon eux, on corrige.

🎮 Compter avant de mesurer

Quatre frames de PRÉDICTION, calquées sur les mesures 4.6 du TP : 1 → 17 → 2. Faire écrire les nombres avant validation. 1. Frame « plat » : la référence (1 requête) — beaucoup surestiment déjà. 2. Frame « deux champs » : le moment clé. 8 produits × 2 relations parcourues DANS le sérialiseur = 16 lectures ajoutées. Faire remarquer qu'aucune erreur, aucun log visible en développement ne l'annonce. 3. Frame « où corriger » : la salle propose souvent le sérialiseur — c'est FAUX, et c'est le point le plus rentable du module : le sérialiseur reçoit des objets déjà chargés, il ne peut qu'aller les chercher un à un. 4. Finir sur queryset : un attribut hérité, deux requêtes, zéro ligne de vue réécrite.

Consommer l'API

Une fois publiée, votre API n'est plus qu'une adresse

Le problème à poser : un autre service (un moteur de recommandation, un back-office) va appeler cette API depuis Python, sans navigateur, sans formulaires. Ce client-là doit annoncer ce qu'il envoie, lire le code AVANT le corps, et savoir distinguer 201, 204, 400 et 405 sans deviner. Tout ce qui suit est du côté client — mais c'est en écrivant le client qu'on comprend le contrat du serveur.

🎮 Cinq frames côté client

Périmètre : le client SERVEUR (requests). Le client navigateur — fetch, onglet réseau — est traité à la partie suivante, uniquement sous l'angle CORS. 1. « json contre data » : l'erreur la plus fréquente en projet. Faire énoncer l'en-tête envoyé par chaque forme. 2. « lire la réponse » : le 200 ne garantit pas une liste non vide — distinction succès HTTP / contenu métier. 3. Le slots des codes reprend 201 / 204 / 400 / 405 vus en partie 3, mais cette fois du point de vue de QUI LES LIT. 4. « la forme demandée » : la négociation de contenu explique pourquoi le navigateur affiche une page HTML et requests reçoit du JSON — même URL. 5. LA FRAME-PONT : le DELETE anonyme possible sur le ViewSet. Laisser la salle conclure que la restriction est côté vue, puis arrêter là — les classes de permission sont l'objet du reste de la journée, et leurs deux refus (qui es-tu ? / as-tu le droit ?) portent deux codes différents que le TP mesure (401 contre 403). Ne PAS donner les codes maintenant.

django-cors-headers

Le même appel réussit en Python — et depuis un navigateur, rien n'arrive au client

Le problème à poser : le front du projet appelle localhost:8000 depuis localhost:3000. requests obtient un 200 impeccable ; le fetch JavaScript, lui, jette la réponse. Même URL, même serveur, même instant — demander ce qui diffère. La frame fait construire la réponse : c'est le NAVIGATEUR qui bloque, au retour.

🎮 Une page, deux origines

UNE frame — le reste est DÉMONSTRATION EN DIRECT, rien à construire de plus (contrat de design §2) : 1. Servir une petite page statique sur un port différent de l'API, tenter le fetch : erreur CORS dans la console, PENDANT QUE la trace serveur montre le 200. Ce décalage est tout le sujet. 2. Installer la solution, trois réglages : pip install django-cors-headers, "corsheaders" dans INSTALLED_APPS, "corsheaders.middleware.CorsMiddleware" AU SOMMET de MIDDLEWARE — rappeler pourquoi : un middleware placé sous un coupeur pourrait ne jamais ajouter ses en-têtes (module II, Chrono sous le Videur). 3. Régler CORS_ALLOWED_ORIGINS = ["http://localhost:3000"], rejouer le fetch : 200 lu cette fois. 4. Montrer la requête préliminaire OPTIONS sur un POST avec en-têtes personnalisés, puis revenir à la règle : seule l'ORIGINE du CLIENT compte ; requests n'en a pas, donc n'est jamais concerné.
